# DSA v2.10 portable verifier work contract

This document defines the Phase-2 integration boundary for portable verifier work certificates.

## Security boundary

A `VerifierWorkCertificate` is a deterministic statement about work implied by an artifact and verifier algorithm. For an identical canonical artifact, verifier version, and work-profile ID, the canonical certificate payload MUST be identical across supported hosts.

The certificate therefore MUST NOT include wall-clock duration, process RSS, tracemalloc peaks, CPU model, scheduler delay, or other host-sensitive observations. Those values are `VerifierRuntimeDiagnostics`. They are useful operational telemetry but are not evidence-integrity facts and are not signed as part of the portable certificate.

## Canonical certificate

`dualstream.work_certificate` emits certificate version 2, adding signed `work_completed` and `work_bounds` fields. Version-1 canonical bytes remain supported; version 1 cannot represent partial work or parser bounds. Canonicalization uses UTF-8 JSON with sorted keys and compact separators. The `signature` field is excluded from the signed payload. Unsupported certificate versions fail closed.

The artifact SHA-256 and work-profile ID are bound into the canonical payload so a valid certificate cannot be transplanted to another artifact or work profile without invalidating its digest/signature.

## Deterministic envelope

A `WorkEnvelope` constrains deterministic counters, including bytes read/hashed, candidate entries, span overlay operations, allocation events, declared maximum live bytes, and full-artifact materializations. `validate_work_envelope` never consults elapsed time or RSS.

The V3.3 verifier uses a bounded streaming path and enforces a portable envelope with `max_full_artifact_materializations = 0`. V3.1 and V3.2 remain readable through the explicitly identified legacy materializing path; those artifacts receive the `legacy-materializing-v1` work-profile ID and do not claim portable V3.3 conformance.

`maximum_live_bytes` is a deterministic wire-buffer bound, not an observation of Python object size or process RSS. It conservatively covers retained header and metadata bytes, two chunk payload buffers, manifest and chunk-header buffers, and a logarithmic Merkle frontier with temporary digests. It excludes decoded Python object sizes, which are bounded separately by chunk and metadata caps. `allocations` counts explicit artifact read-buffer events, including the dispatch read; it is not a Python allocator measurement. Host-observed peaks remain runtime diagnostics.

## Outcome semantics

Deterministic work-envelope violations are evidence/verifier-contract failures and map to AST 523 (`AST_DETERMINISTIC_VERIFIER_WORK_VIOLATION`). Host resource instability is different: if verification cannot complete because of timing or resource conditions, the result is `INCONCLUSIVE_INFRA`, never PASS and never an evidence-integrity FAIL.

2. [x] Add a bounded streaming decoder for CI-Lite and CI-Standard.
3. [x] Construct `VerifierWorkCertificate` from the streaming counters.
4. [x] Validate the certificate against the profile's registered `WorkEnvelope`.
5. [x] Map deterministic violations to AST 523.
6. [x] Emit `VerifierRuntimeDiagnostics` separately and exclude it from certificate signing.

8. [ ] Confirm the configured golden-certificate CI matrix passes on Linux, Windows, and macOS for the combined revision.

## Current status

The canonical certificate type is now integrated into `verify_evidence_artifact`. V3.3 verification reads one bounded chunk at a time, calculates artifact and content hashes incrementally, verifies chunk integrity and manifest aggregates, and emits deterministic counters. Authorized keyed replay uses at most four additional sequential token passes through the shared replay validator. The parser retains O(chunk-size + log(chunk-count)) wire data. Missing audit keys fail closed and failed checks preserve partial work counters. Adjacent run metadata is capped before reading, including directory-based artifact lookup.

Local integration tests assert that V3.3 does not call `Path.read_bytes()`, that canonical certificate bytes are identical across repeated runs despite separate runtime diagnostics, that deterministic envelope violations map to AST 523, and that keyed replay remains zero-materialization. A separate CI matrix installs NumPy (required by the package imports) and runs `python -m scripts.check_portable_certificate` from the repository root to check the same golden certificate digest on Linux, Windows, and macOS.

## Streaming v2 profile limits

The work-profile ID is the evidence profile ID for verifier work with the suffix
`:streaming-v2`. Its envelope allows at most six artifact lengths read (including
dispatch), twelve artifact lengths submitted directly to SHA-256, five times the
profile maximum K candidate decodes per token, 64 fixed read-buffer events plus
16 per token and 3 per span, and zero full-artifact materializations. The logical
wire-residency ceiling is 1 MiB plus 512 bytes per token. These conservative limits
include the four permitted replay passes. HMAC internals, calibration, and
adjacent metadata are outside these artifact work counters. Parser caps are
signed separately and checked before variable-size reads. Work envelopes remain
mandatory when callers disable profile byte-budget evaluation.

Legacy certificates explicitly use `legacy-materializing-v1`, report full
materializations, and use null for unmeasured hash/allocation/residency fields.
They do not satisfy the streaming envelope. A failed certificate has
`work_completed=false`; its counters are lower bounds on interrupted work and
must not be treated as successful verification or storage attestation.
